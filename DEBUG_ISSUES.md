## 🔍 Обнаруженные проблемы

### 1. **Пользователь видит только часть пресетов вместо всех**

**Проблема:**
- При синхронизации пользователь видит только 2 пресета (из `user_saved_presets` с `sync_enabled=True`), хотя у него больше пресетов
- API `/my-presets` возвращает только пресеты из `user_saved_presets` с `sync_enabled=True`
- Пресеты, созданные напрямую пользователем (где `preset.user_id == current_user.id`), не возвращались, если их не было в `user_saved_presets`

**Причина:**
- API `/my-presets` использовал только `user_saved_presets` с `sync_enabled=True`
- Если пресет был создан напрямую (через UI или API) до добавления логики `user_saved_presets`, он может отсутствовать в таблице
- Или если пресет был создан, но запись в `user_saved_presets` не была создана по какой-то причине
- Это проблема для ЛЮБОГО пользователя, не только для админа

**Решение:**
✅ **Исправлено в `backend/app/api/v1/endpoints/auth.py`:**
- Теперь API возвращает пресеты из двух источников:
  1. Из `user_saved_presets` с `sync_enabled=True` (основной путь)
  2. Прямо созданные пользователем пресеты (`preset.user_id == current_user.id`), которых нет в `user_saved_presets`

**Код:**
```python
# 1. Пресеты из user_saved_presets
saved_query = select(UserSavedPreset).where(...)

# 2. Пресеты, созданные напрямую пользователем (для совместимости)
direct_presets_query = select(Preset).where(
    Preset.user_id == current_user.id,
    Preset.active == True,
    ~Preset.id.in_(list(preset_ids))  # Исключаем уже найденные
)
```

### 2. **Ошибка "Error parsing server response: Unknown exception"**

**Проблема:**
- При переходе в профиль появляются ошибки "Error parsing server response: Unknown exception"
- Неясно, что именно пошло не так, так как не логируется тело ответа

**Причина:**
- Ошибки парсинга JSON ловятся через `catch (const std::exception& e)`, но `catch (...)` может не перехватывать все исключения
- Тело ответа от сервера не логируется, что затрудняет отладку

**Решение:**
✅ **Добавлено детальное логирование:**
- Добавлен `catch (...)` для перехвата всех исключений
- Логируется тело ответа (первые 500 символов) для отладки
- Более информативные сообщения об ошибках

**Места, где улучшено логирование:**
- `update_user_info()` - при парсинге ответа `/me`
- `export_filament_presets_to_filamenthub()` - при проверке разрешений
- `export_printer_profiles_to_filamenthub()` - при проверке разрешений
- `export_print_profiles_to_filamenthub()` - при проверке разрешений
- Все места парсинга JSON ответов от API

### 3. **Логи OrcaSlicer - где они пишутся?**

**Вопрос:** Где OrcaSlicer пишет логи и стоит ли их сохранять для отладки?

**Ответ:**
- OrcaSlicer использует `BOOST_LOG_TRIVIAL` для логирования
- По умолчанию логи пишутся в стандартный вывод (stdout/stderr)
- В Windows обычно логи можно найти:
  - В папке рядом с `orca-slicer.exe`
  - В `%APPDATA%\OrcaSlicer\logs\` (если настроено)
  - Или в консоли, если запускается из командной строки

**Рекомендация:**
- Для отладки можно настроить запись логов в файл
- Или добавить кнопку "Export logs" в настройки FilamentHub Panel
- Или автоматически сохранять логи с префиксом `FilamentHub:` в отдельный файл

**Где искать логи:**
1. В консоли, если запускается из командной строки
2. В папке с `orca-slicer.exe` (файлы `.log`)
3. В `%APPDATA%\OrcaSlicer\` (если настроено)

**Временное решение:**
- Можно добавить функцию сохранения последних 1000 строк логов в файл
- Или добавить кнопку "Copy logs" для копирования в буфер обмена
